# MyCLI 2.4.0 plan: discover reasoning levels from chat templates

Status: plan, 21 November 2026. Not started.

## Goal

`/reasoning` should work for any local model without a hand-written `[local.<name>]` profile. mycli reads each oMLX model's chat template, finds the reasoning levels the template supports, caches them, and lets the user store a preferred level per model.

Today, for a local model without a profile, `/reasoning` prints "No reasoning levels configured for this model". On 21 Nov 2026 the user added `[local.inkling]` by hand after finding that Inkling-2-Mini at `low` is fast and good, while its template default (`high`) is slow.

## What the templates look like

Survey of the 15 models with a chat template under `~/AI/models/llms` (21 Nov 2026):

| Pattern | Models | Levels the template accepts |
|---|---|---|
| Value map + validation | `mlx-community_Inkling-2-Mini-oQ4e-mtp` | `effort_map` keys: none, minimal, low, medium, high, xhigh, max. Unknown values `raise_exception`. Unset = 0.9 (= `high`). `xhigh` and `max` both map to 0.99. Floats in [0, 0.99] also accepted. |
| Allow-list + validation | `orcarouter_Qwen3.8-27B-Uncensored-oQ8e-mtp`, `RadixArk_DaisyRose-27B-oQ8e-mtp`, `Blackfrost-AI_CYBER-FROST-3.8-oQ5e-mtp` | `reasoning_effort\|default('xhigh')`, then `not in ('xhigh', 'medium', 'low')` raises. |
| Comparisons, no validation | `orcarouter_Nex-N2.5-mini-Uncensored-oQ8e` | `== 'none'`, `== 'high'`; anything else falls through to the unset branch. |
| Thinking switch only | Qwen3.6-35B, Ornith-1.5-122B, MiMo-V2.6 (both), Ling-3.0-flash | `enable_thinking` only → `/thinking on\|off`. |
| No reasoning control | flint, Ripple-65B, RedSage, Llama-Primus-Nemotron, WhiteRabbitNeo | none. |
| Built into mycli already | Cold-Fusion (`levels()` in `cersei-provider/src/reasoning.rs`) | low, medium, xhigh, einstein, spoon. |

Known from Hugging Face but not installed: Hy4-flash validates `reasoning_effort not in ['max', 'high', 'no_think']` and raises otherwise.

Conclusion: the levels can be found by **rendering the template** with each candidate value and comparing the output. A static regex alone misses cases (Nex has no allow-list; Inkling's levels are dict keys).

## Design

### 1. Find the template

For each model id from `/v1/models` (already fetched in `repl.rs`, see `fetch_models`/`/v1/models` helpers around line 512):

1. **Model folder.** Ask oMLX's admin API `GET /admin/api/models`, which includes `model_path` per model. If that endpoint needs an admin session rather than the API key (to verify in step 1 of the work), fall back to the model directories from `~/.omlx/settings.json` (`model_dirs` or `base_path`) and match the folder name to the model id. oMLX also writes generated folders for GGUF models under `<base_path>/gguf/`, which contain a `chat_template.jinja`.
2. **Template source**, first that exists: `chat_template.jinja`; `tokenizer_config.json` → `chat_template` (a string, or a list of `{name, template}` where `name == "default"`).
3. **Special tokens** for rendering: `bos_token`, `eos_token` from `tokenizer_config.json` (strings or `{content: …}` objects).

Only works when mycli runs on the oMLX machine. Remote oMLX: see "Later: oMLX reports levels" below.

### 2. Render and classify

New module `crates/mycli/src/reasoning_discovery.rs`, using [minijinja](https://crates.io/crates/minijinja) with `minijinja-contrib`'s `pycompat` (Python string/dict methods such as `.items()`, `.startswith()`, `.strip()`), plus mycli-provided `raise_exception(msg)` (returns an error), `strftime_now(fmt)` and a `tojson` filter.

Render context, the same for every call: `messages = [{"role": "user", "content": "hi"}]`, `add_generation_prompt = true`, no `tools`, the special tokens above, and **only** the variable under test.

Steps for one template:

1. **Baseline**: render with `reasoning_effort` unset. A baseline error → discovery fails for this model (status `unrenderable`, error kept for `/reasoning discover` output).
2. **Candidates**: the standard names `none, minimal, low, medium, high, xhigh, max, on, off, no_think` plus every short string literal (`[a-z][a-z0-9_]{1,15}`) that appears on a template line mentioning `reasoning_effort` or a variable assigned from it (`set x = reasoning_effort…`, followed one level). This catches `einstein`/`spoon`-style custom names.
3. **Render each candidate** as `reasoning_effort = "<candidate>"`:
   - render error (e.g. `raise_exception`) → not supported;
   - output differs from the baseline → **supported level**;
   - output equals the baseline → supported only if the candidate appears as a literal in a reasoning line (then it is the **template default**, e.g. Inkling `high`, Qwen3.8 `xhigh`); otherwise ignored (Nex silently ignores `medium`).
4. **Aliases**: candidates with identical output are grouped (Inkling `xhigh` = `max`). All names stay selectable; the picker shows "same as xhigh".
5. **Thinking switch**: if no level is found, render with `enable_thinking = true` and `false`. Different outputs → `thinking_switch = true` (the UI points to `/thinking on|off`).
6. **Ordering**: keep the standard order (none < minimal < low < medium < high < xhigh < max), then custom names in template order.

Result per model:

```rust
pub struct Discovered {
    pub levels: Vec<String>,          // ordered, aliases included
    pub template_default: Option<String>,
    pub aliases: Vec<(String, String)>,
    pub thinking_switch: bool,
    pub template_sha256: String,
    pub status: Status,               // Ok | NoControl | Unrenderable(String) | NotFound
}
```

### 3. Cache and per-model preset

File `~/.config/mycli/reasoning.toml`, readable and hand-editable:

```toml
[models."mlx-community_Inkling-2-Mini-oQ4e-mtp"]
levels = ["none", "minimal", "low", "medium", "high", "xhigh", "max"]
template_default = "high"
aliases = { max = "xhigh" }
preset = "low"                       # set by the user; applied when the model is selected
template_sha256 = "…"
discovered = "2026-11-21"
```

- An entry is rediscovered when the template's SHA-256 changes (hashing a small file on `/model` is cheap).
- `preset` survives rediscovery. If the preset is no longer among the levels, it is dropped with a notice.
- Writes go through a temp file + rename, like mycli's other state files.

### 4. Precedence

`Config::reasoning_choices()` and `validate_reasoning()` (config.rs ~398–408) and the provider's `validate_with_levels` (openai.rs ~258):

1. `reasoning_levels` in the active `[local.<name>]` profile (unchanged; `[]` still disables levels);
2. discovered levels from `reasoning.toml` (new, local providers only);
3. built-in `levels()` in `cersei-provider/src/reasoning.rs` (unchanged).

Starting effort when a model is selected: explicit `reasoning_effort` in the profile/config, else the cached `preset`, else none (server default). `{REASON:…}` tags keep their current behaviour.

The provider currently receives configured levels only via `reasoning_levels_override()` and only checks them for `default_model`. The builder call in `repl.rs` (~491) passes the resolved list (profile or discovered), so the provider's validation matches what the UI offers. When `/model` switches models, the agent is rebuilt as today, with the new model's list.

### 5. Commands

| Command | Effect |
|---|---|
| `/reasoning` | Picker as today. For a model with discovered levels, shows them with "(template default)", "same as …", and the current preset. |
| `/reasoning <level>` | As today; validated against the resolved list. |
| `/reasoning preset <level>` | Store `<level>` as this model's preset in `reasoning.toml` and apply it now. `/reasoning preset default` removes it. |
| `/reasoning discover` | Discover for the current model and show the result. |
| `/reasoning discover all` | Discover for every model in `/v1/models`; print a table (model, levels, default, preset, status). |
| `mycli --discover-reasoning [MODEL]` | Same as `discover all` / one model, non-interactive; exits 0 and prints the table. |

The "No reasoning levels configured" notice changes to point at `/reasoning discover` when discovery has not run, and to `/thinking on|off` when the template only has the thinking switch.

Automatic discovery: on `/model` and at startup, if the selected local model has no cache entry or a changed template hash, discover it silently (rendering takes milliseconds; nothing is loaded on the server). Failures only log; `/reasoning discover` shows details.

## Work steps

1. **Probe**: confirm `GET /admin/api/models` with the API key returns `model_path`; otherwise implement the settings-file fallback. Confirm `~/.omlx/settings.json` field names for model directories.
2. **Fixtures**: copy the templates of the patterns above into `crates/mycli/tests/fixtures/templates/` (Inkling, Qwen3.8-27B allow-list, Nex comparisons, Qwen3.6 thinking-only, flint none) plus a synthetic Hy4-style and Cold-Fusion-style template. Record expected `Discovered` values in the tests.
3. **Discovery module**: minijinja environment, candidate extraction, classification, aliases, ordering. Unit tests per fixture, including the edge cases: template default equal to baseline, aliases, unknown value raising, unknown value ignored, unrenderable template.
4. **Template lookup**: admin API / settings fallback, `chat_template.jinja` vs `tokenizer_config.json` (string and list forms), special tokens. Tests with temp dirs.
5. **Cache**: `reasoning.toml` read/write, hash check, preset preservation, atomic write. Tests.
6. **Precedence wiring**: `Config`, builder, provider validation; tests that a profile list still wins and `[]` still disables.
7. **Commands and UI**: `/reasoning preset`, `/reasoning discover [all]`, picker annotations, `--discover-reasoning`, updated notices, status line.
8. **Docs**: README "Local reasoning levels" section, `config.example.toml` (reasoning.toml mention), `docs/releases/2.4.0.md`.
9. **Live check** against oMLX 0.8.2 on this Mac: `--discover-reasoning` over all installed models matches the survey table; Inkling at `low` vs `high` shows the expected speed difference on a real task; profile `[local.inkling]` still overrides; a model with a hand-edited preset starts at that level.
10. **Release** per `mycli-release-process`: version 2.4.0 in `crates/mycli/Cargo.toml` and the README banner, notes file, commit, annotated tag, push (only when the user asks).

## Dependencies

- `minijinja` (with `loader` off, `builtins` on) and `minijinja-contrib` (`pycompat`). Both pure Rust, no system libraries; they keep the release-binaries workflow (linux arm64/x86_64, macOS arm64/x86_64) unchanged.
- `sha2` for the template hash; already in `Cargo.lock`, so only a dependency line in `crates/mycli/Cargo.toml` if mycli doesn't use it yet.

## Risks and limits

- **Template compatibility.** Hugging Face templates are written for Python Jinja. Unsupported constructs make discovery fail for that model (`unrenderable`), never the session; the model then behaves as today. The fixtures cover the patterns in use.
- **Levels accepted ≠ levels useful.** Discovery only says what the template accepts. Which level is best stays the user's choice, stored as `preset`.
- **Numeric efforts** (Inkling accepts floats) are not offered; only named levels.
- **Rendering with minimal messages** might miss reasoning blocks that only appear with tools or system prompts. Mitigation if a fixture shows it: render a second context with a system message and one tool, and merge.
- **Local only** until oMLX reports levels itself.

## Later: oMLX reports levels

An upstream oMLX PR could add the same information to `/v1/models` (for example `reasoning_efforts`, `reasoning_default`, `thinking_switch`), computed server-side from the loaded template with Python Jinja, which avoids compatibility gaps. mycli would then prefer the server's list and keep local discovery as the fallback, which also makes remote oMLX servers work. Not part of 2.4.0.
